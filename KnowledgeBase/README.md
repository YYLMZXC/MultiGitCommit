# 知识库

按「**换一个项目还能不能用**」把经验分成两类，避免项目细节和通用工程经验混在一起。

| 目录 | 定位 | 迁移到下一个项目时 |
|---|---|---|
| [`project-specific/`](project-specific/) | 项目独立：依赖本项目的业务规则、目录结构、包名、配置字段、特定实现 | 留在原仓库，仅供对照 |
| [`reusable/`](reusable/) | 可复用：依赖工具链 / 框架机制 / 错误码 / 工程习惯，与业务无关 | 直接复制作为新项目的踩坑清单 |

## 分类判定

- 结论里出现本项目的业务概念（提交格式、皮肤区域、仓库配置字段、ApplicationId、具体目录名）→ `project-specific/`。
- 结论是「某个工具/框架在什么条件下会报什么错、怎么绕」（XA4216、XA0035、IDE 回写 csproj、中文乱码、响应式布局套路）→ `reusable/`。
- 框架机制可复用，但**具体版本号、包名、目标框架组合**属于项目现状 → 机制写 `reusable/`，现状写 `project-specific/`。
- 一条经验两部分都有时拆成两条，各自注明来源项目，不要整段复制。

## 记录模板

```markdown
## <一句话结论>
- 日期：YYYY-MM-DD
- 来源项目 / 文件：
- 现象 / 报错码：
- 原因：
- 做法：
- 验证方式：（构建命令、冒烟测试、真机结果；未验证写「未核验」）
- 适用边界：（哪个 TFM / 版本 / 平台下成立）
```

## 维护约定

- 每条结论必须可追溯：写清来源文件与验证方式；历史会话整理而来、本次未重新核验的条目标注「历史记录，未核验」。
- 版本升级导致结论失效时，不删除，改写为「旧结论 + 失效版本 + 新结论」，便于以后对照。
- 新经验先追加到最接近的文件；同类条目积累到一定量再按主题拆分文件。
- `reusable/` 中的条目尽量写成可直接执行的命令或可复制的代码结构，不写「注意一下」这类空话。
